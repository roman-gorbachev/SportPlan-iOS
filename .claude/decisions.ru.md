# Журнал решений (этап 0, 17.11.2026)

Источник решений для `docs/code-brief.md` и `.design/design-brief.md`. Разработка идёт этапами, каждый этап обсуждается отдельно.

## Правила проекта
Из CLAUDE.md scryptowallet берём: один тип на файл, без комментариев, именованные константы, явный `return`, все строки через String Catalog; слои `presentation → domain → data`; композиция в `AppDIContainer`; `@Observable` ViewModel + `UiState`; `XRoute` / `XScreen`; `Router` на `NavigationPath`; токены темы; SF Symbols; формат коммитов без упоминаний AI; документы Claude на русском в `.claude/`.

Отличия от scryptowallet:
- есть тестовый таргет;
- async/await вместо Combine;
- нет DataSource-слоя;
- свой стек навигации в каждой вкладке;
- нет wide-раскладки (только iPhone).

Собственный CLAUDE.md для sportplan заводим на этапе каркаса.

## Предметная модель
- Тип упражнения — две оси: **оборудование** и **метрика** (вес × повторы / время).
- **Оборудование** — отдельная сущность для всего железа: грифы, гантели, тренажёры. `kind`: barbell | dumbbell | plate_loaded_machine | selectorized_machine. Вес грифа/платформы и шаг веса живут в оборудовании; глобальных «вес грифа» и «шаг веса» нет.
- Упражнение без оборудования — собственный вес (в домене enum, не голый nil).
- **Один зал**: оборудование и блины к залу не привязаны.
- Справочник при первом запуске пустой, быстрое добавление.
- Упражнения и оборудование не удаляются, а архивируются. Архивация упражнения убирает его из программ (подтверждение «будет убрано из N дней»), история не трогается.
- Если по упражнению есть подходы: метрику менять нельзя, оборудование — только на оборудование того же вида.
- `WorkoutExercise` между `Workout` и `SetEntry` хранит копию целей на момент тренировки.
- Цели повторов — диапазон min–max (одно число = min == max).
- Плановые подходы хранятся в БД с `completed_at = NULL`; при «Завершить» невыполненные удаляются.
- Подход на время — секундомер (счёт вверх); отдых — таймер обратного отсчёта.

## Архитектура
- Хранилище **GRDB**: миграции через `registerMigration`, внешние ключи.
- Реактивность: async/await, `ValueObservation.values(in:)`, подписка в `.task {}` на Route.
- Локальный Swift Package: `Domain` (модели, протоколы репозиториев, use cases, чистые расчёты; `nonisolated`, `Sendable`) и `DesignSystem` (токены и базовые компоненты, общие с виджетом).
- Приложение: `presentation/`, `data/` (GRDB), `di/`. Widget Extension для Live Activity.
- `XRepository` / `XRepositoryImpl` прямо поверх `AppDatabase`, без DataSource. Отдельные классы только для внешних систем (уведомления, ActivityKit, файлы).
- ViewModel обращается только к use cases, даже к простым пробросам.
- Свой `NavigationStack` и `Router` в каждой вкладке, чтобы таймер в `tabViewBottomAccessory` был виден на любой глубине.
- Активная тренировка — `workout` без `finished_at`, переживает перезапуск. Таймер отдыха хранит только `endDate`. Один долгоживущий владелец этого состояния в `AppDIContainer`.
- Тесты на Swift Testing: домен через `swift test`, репозитории на in-memory GRDB.

## Схема БД v1
Соглашения:
- ключи UUID;
- вес в граммах `INTEGER` (в домене тип `Weight`);
- порядок — `position INTEGER`;
- даты в UTC, дни для heatmap группируются в Swift по локальному календарю;
- одна миграция `v1`; после появления реальных данных существующие миграции не редактируются;
- индексы на все FK явно.

```
equipment          id, name, kind, base_weight_g (0), weight_step_g, is_archived, created_at
exercise           id, name, description?, equipment_id? → equipment RESTRICT,
                   metric (weight_reps | duration), rest_sec (90), is_archived, created_at
program            id, name, position, created_at
program_day        id, program_id → program CASCADE, name, position
planned_exercise   id, program_day_id → program_day CASCADE, exercise_id → exercise RESTRICT,
                   position, target_sets, target_reps_min?, target_reps_max?, rest_sec
workout            id, program_day_id? → program_day SET NULL, program_day_name? (копия),
                   started_at, finished_at?, note?
workout_exercise   id, workout_id → workout CASCADE, exercise_id → exercise RESTRICT,
                   position, target_sets?, target_reps_min?, target_reps_max?, rest_sec
set_entry          id, workout_exercise_id → workout_exercise CASCADE, position,
                   weight_g (0), reps?, duration_sec?, is_warmup, completed_at?
plate              id, weight_g UNIQUE CHECK(250…50000), color_hex
```

- Дополнительные индексы: `workout(started_at)`; частичный уникальный индекс `workout WHERE finished_at IS NULL` (одна активная тренировка).
- Таблицы `settings` нет; `UserDefaults` только для мелочей UI.

## Логика
Везде учитываются только выполненные рабочие подходы.

- **Раскладка блинов** (barbell, plate_loaded_machine):
  - на сторону `(вес − base_weight) / 2`;
  - точный подбор (ДП в граммах): число блинов не ограничено, выбираем минимум блинов, при равенстве — более тяжёлые;
  - если вес не собирается или он меньше грифа, стопки нет; если вес равен грифу — пустой гриф.
- **Рекорды**:
  - с оборудованием — макс. вес и лучший расчётный 1ПМ по Эпли (1ПМ только при reps ≤ 12);
  - свой вес — по Парето: подход рекордный, если раньше не было подхода, где и отягощение, и повторы не меньше;
  - на время — макс. длительность;
  - бейдж сравнивает подход со всем, что было до него; равенство — не рекорд; без истории бейджа нет.
- **Предзаполнение**: строк столько, сколько `target_sets`. Значения берутся из рабочих подходов прошлой тренировки по номеру; если их меньше, повторяется последний. Разминку пользователь добавляет сам. Для тренировки вне плана — по структуре прошлой.
- **Прогрессия** (только оборудование + вес × повторы):
  - условие: у прошлой тренировки есть цели, рабочих подходов ≥ `target_sets`, в каждом reps ≥ `target_reps_max`;
  - предлагаем макс. рабочий вес + `weight_step`;
  - тап подставляет вес во все невыполненные рабочие подходы.
- **Графики** (точка = тренировка):
  - с оборудованием — лучший 1ПМ или макс. вес (переключатель);
  - свой вес — макс. повторов;
  - на время — макс. длительность.
- **Heatmap**: рабочие подходы за локальный день, уровни 0 / 1–6 / 7–12 / 13–18 / 19+.
- «Объём» не считаем — нигде не отображается.
- Шаг отягощения для своего веса — 2.5 кг (константа).
- Таймер отдыха стартует после любого выполненного подхода, длительность из `workout_exercise.rest_sec`.

## Этап 3.2: справочник упражнений (обсуждение 18.11.2026)
- Метрика «Время» есть только у упражнений с собственным весом. У штанги, гантелей и тренажёров метрика всегда «Повторы», переключатель в шаге 2 скрыт: у подхода на время вес не записывается, и оборудование хранилось бы впустую. Это расходится с макетом, отмечено в design-brief.
- Подтверждение архивации, когда упражнения нет ни в одном дне: тот же диалог с текстом «Упражнение пропадёт из справочника. История сохранится.» Текст наш, дизайнеру отмечено.
- Одинаковые названия разрешены: «Жим лёжа» на олимпийском грифе и в Смите различаются подписью оборудования.
- Оборудование в шаге 2 выбирается сразу, только если в зале одно подходящее. Если их несколько, не выбрано ничего, «Добавить» неактивна до выбора: случайно сохранённый не тот гриф исказил бы веса в истории.
- Без возражений приняты:
  - вход — строка «Справочник упражнений N» на вкладке «Программы», остальное там заглушка до этапа 4;
  - группы «Свободный вес» / «Тренажёры» / «Собственный вес», внутри по названию, подпись «оборудование · метрика»;
  - вид упражнения не хранится, он выводится из вида оборудования или собственного веса;
  - чип открывает sheet сразу на шаге 2, «Назад» ведёт на шаг 1;
  - «Новый гриф» открывает редактор из 3.1 вторым sheet, сохранённое оборудование выбирается сразу;
  - тап по строке справочника ничего не делает до дизайна правки, только swipe «Архивировать»;
  - блок «В день A · Подходы» — этап 4.

## Этап 4: программы (обсуждение 18.11.2026)
- В макетах нет форм создания программы и дня, меню «…» программы, sheet целей упражнения в дне и выбора упражнения из справочника. Presentation этапа 4 ждёт этих макетов, задачи записаны в `.design/design-brief.md`. Пока делаем Domain и data программ: они от форм не зависят.

- Программы и дни удаляются по-настоящему (CASCADE) с подтверждением; история хранит копии названия дня и целей.
- Порядок упражнений в дне меняется в «Править»; порядок дней и программ в этом этапе не меняется.
